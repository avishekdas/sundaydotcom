| M0B-1 | **blocking** | **The gap-sync cursor can silently skip changes**, which breaks the "a change can never be skipped" contract (arch 03 §3.3a) on exactly the reconnect path M0b certifies. (a) Rows are capped with `limit 1000`, yet `next_since_xmin` is always the current snapshot xmin. A client that missed more than 1,000 changes on a board (one bulk edit, or a long offline period) gets the first 1,000 and its cursor jumps past the rest for good. (b) Rows older than 25 h are filtered out, but no `410 resync` is returned (03 §3.3a requires it). An old cursor quietly returns a partial set, and once partitions are dropped (2 days) it returns nothing. The client then believes it is in sync. The xid/xmin logic itself is correct: windows `[since, xmin)` are contiguous and disjoint, and xmin is monotonic, so with no cap and no age filter each change is returned exactly once. | `backend/src/tasklane/workmgmt/boards.py:231-237`; `web/src/sync/engine.ts:97-108` (no truncation or 410 handling); `test_board_service.py:91` (3 rows only) | When the cap is hit, return `truncated: true` (or set the cursor to the last returned row's xid and page). Return 410 when `since_xmin` is older than the retention window; the server can keep the oldest retained xid per board or compare against the partition floor. In the client, handle `truncated`/410 with a full `load()`. Add tests: 1,001 changes, an expired cursor, and an in-flight transaction that commits after the cursor read (two connections). |
